# 仓库结构收口与最小落地设计文档

- 日期: 2026-08-17
- 主题: 结构收口与最小落地
- 适用仓库: `d:\Project_env\newenergycoder.club`

## 1. 背景

当前仓库的真实形态是一个基于 `React + TypeScript + Vite` 的官网型单页应用，叠加站内 Markdown 文档系统、一个 Vercel Serverless 报名接口和若干内容/构建脚本。

现阶段的主要问题不是功能完全不可用，而是仓库的真实实现边界、目录结构、文档描述和预留模块之间已经出现明显偏差，具体表现为：

- 技术架构文档描述了未实现的平台化能力，如微服务、Supabase、Redis、React Query 等。
- 主路由集中在 `src/App.tsx`，同时存在未接入的学习中心路由配置。
- 资源数据同时存在于 `src/data/*`、页面内 `mock` 数据和悬空的 API 抽象中，数据来源不统一。
- 认证与受保护路由采用 mock 语义，但页面访问边界已经开始表现出“生产可用”的假象。

本次工作的目标不是平台化扩张，而是先把仓库收口到“真实、清晰、低风险可维护”的状态，并在此基础上完成少量最小落地。

## 2. 目标

本次改动的目标如下：

- 让技术文档准确反映当前真实架构。
- 收敛路由层，消除未接线或含义不清的路由配置。
- 明确当前主数据来源，减少静态数据、页内 mock 数据和未来 API 抽象之间的冲突。
- 明确 mock 认证与受保护路由的边界，避免误导。
- 在不引入平台化复杂度的前提下，完成最小、低风险的落地整理。

## 3. 非目标

以下内容不在本次范围内：

- 不接入真实 Supabase、Redis、数据库或缓存层。
- 不实现真实 OAuth、用户体系或权限体系。
- 不按旧文档目标继续扩展为完整学习平台、社区平台或微服务平台。
- 不进行与本次目标无关的大规模 UI 重构。
- 不新增大而全的测试体系，仅做必要的最小验证。

## 4. 推荐执行顺序

### 4.1 第一步：修正文档真相

先更新 `public/docs/technical/architecture.md`，让其准确反映当前仓库的真实结构：

- 官网 SPA 前端应用。
- Markdown 文档内容系统。
- `/api/join` 报名接口。
- 构建、SEO、内容同步脚本。

应移除或重写未落地能力的表述，包括但不限于：

- API 网关与服务层拆分。
- 微服务架构。
- Supabase、Redis、SendGrid、OpenAI API。
- React Query、React Hook Form、Prettier、Husky 等当前仓库未实际使用的依赖与流程。

#### 本步骤验收标准

- 架构文档与当前代码、依赖、目录职责一致。
- 新成员仅通过文档即可形成接近真实的系统认知。
- 不再把“未来规划”写成“当前已实现能力”。

### 4.2 第二步：收敛路由层

本步骤聚焦于梳理 `src/App.tsx` 与 `src/routes/learningRoutes.tsx` 的关系，目标是消除“有配置但不生效”的状态。

建议采用以下策略：

- 保留 `App.tsx` 作为当前主路由入口。
- 对学习中心相关路由做一次明确决策：
  - 若当前学习中心页面可稳定访问且语义明确，则将 `learningRoutes.tsx` 正式接入。
  - 若当前学习中心尚未准备好，不应继续保留完整但未启用的路由体系，应删除、冻结或显式标记为未启用。

本次更偏向低风险收口，因此优先推荐：

- 不新增新的复杂路由抽象层。
- 先做“接入或清理”的单一决策，而不是同时引入新的路由框架。

#### 本步骤验收标准

- 仓库内不存在明显的死路由配置。
- 路由定义与实际可访问页面一一对应。
- 后续维护者可以清楚判断哪些页面是正式路由、哪些是保留模块。

### 4.3 第三步：统一数据来源

本步骤聚焦于资源类页面和静态内容的真实数据来源。

推荐策略为：

- 将 `src/data/*` 作为当前阶段的主数据来源。
- 清理页面级内嵌 `mock` 数据，优先复用 `src/data/resources.ts` 等已有模块。
- 对 `src/services/api.ts` 做定位整理：
  - 如果近期不会启用真实后端接口，则应明确其为未来预留模块，避免被误认为当前主链路。
  - 如果其内容与当前实现明显冲突，且没有近期开启计划，则应考虑删除或收缩为注释化占位。

本次最小落地重点是：

- `ResourcesPage` 不再维护独立数据真相。
- 静态页面以统一的数据模块为准。

#### 本步骤验收标准

- 资源相关页面的数据来源清晰且单一。
- 页面展示与 `src/data/*` 保持一致。
- 仓库内不再同时存在多个“看起来都像主数据源”的入口。

### 4.4 第四步：明确认证语义

当前 `auth-store` 与 `ProtectedRoute` 已经形成了“有鉴权”的结构外观，但真实逻辑仍是 mock 级别。

本步骤不实现真实认证，仅做边界澄清：

- 明确相关页面当前仅依赖本地 mock 登录态。
- 避免后台页、仪表板页被误解为已具备真实安全保护。
- 如有必要，对页面文案、注释或模块命名进行微调，使语义与真实状态一致。

#### 本步骤验收标准

- 维护者能够一眼判断当前鉴权能力的真实等级。
- 不再把 mock 权限边界当作真实权限系统使用。
- 相关代码的命名、说明或调用方式与当前实现一致。

### 4.5 第五步：补最小验证

本步骤不引入完整测试体系，重点是保证本轮收口不会破坏当前可运行状态。

建议至少完成以下验证：

- 类型检查或构建检查。
- 与路由、资源数据、文档页相关的基础运行验证。
- 如果某个改动存在较高回归风险，可补一个最小的聚焦测试，而不是泛化增加测试框架。

#### 本步骤验收标准

- 项目可正常构建。
- 本轮涉及的关键页面未出现明显回归。
- 文档、路由、资源数据与代码状态相互一致。

## 5. 实施原则

本轮改动遵循以下原则：

- 优先修正“认知错误”，再修正“结构松散”。
- 优先做低风险、可验证、不会引入新概念层的改动。
- 不把“未来可能会做”的能力继续伪装成“当前已实现”。
- 对现有代码做目标内重构，不做无关清理。
- 所有代码和文档变更都围绕“真实边界”展开。

## 6. 风险与处理策略

### 6.1 文档回写过度简化

风险：把原架构文档改得过于简略，失去指导价值。

处理策略：

- 保留真实的模块划分、运行链路和部署方式。
- 将“未来规划”与“当前实现”明确拆开描述，避免混写。

### 6.2 路由清理误删未来模块

风险：清理未接线路由时误删近期要启用的页面。

处理策略：

- 在真正删除前先确认页面是否有当前使用入口。
- 若短期内会接入，则优先接线；否则再清理或冻结。

### 6.3 数据统一过程中引入页面展示差异

风险：从页内 mock 数据切回统一数据模块后，页面展示字段可能变化。

处理策略：

- 先对比字段结构与页面消费方式。
- 优先做同构替换，不在本轮顺带改变展示设计。

### 6.4 鉴权边界澄清影响现有演示流程

风险：边界澄清后，某些演示页的访问体验变化。

处理策略：

- 本轮重点是“语义准确”，不是“强化拦截”。
- 除非存在明显误导，否则优先以文案/注释/说明收口，而非大幅改变交互流程。

## 7. 预期交付物

本轮完成后，预期交付物包括：

- 一份与当前实现一致的架构文档。
- 一套路由边界更清晰的入口组织。
- 一个统一的资源数据来源。
- 一套语义更明确的 mock 鉴权边界。
- 一次可复现的最小验证结果。

## 8. 实施后的理想状态

完成本轮后，仓库应达到以下状态：

- 文档描述的系统，和代码里真正运行的系统基本一致。
- 维护者可以快速判断哪些模块是正式能力，哪些模块是预留或演示态。
- 页面、数据、路由与接口边界更加清晰。
- 仓库更适合作为后续逐步演进的平台基础，而不是继续积累“假架构”。

## 9. 后续计划边界

如果本轮收口完成且效果稳定，后续才适合讨论以下增量方向：

- 是否引入真实后端数据层。
- 是否将学习中心从预留模块升级为正式业务模块。
- 是否引入真实认证与权限体系。
- 是否建立更系统的自动化测试与发布护栏。

这些内容需要单独立项，不应在本轮“结构收口与最小落地”中顺带推进。
